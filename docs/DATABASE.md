# Database design

## Current status

The migrations create `profiles`, `goals`, `goal_milestones`, and `tasks`, each protected by per-user RLS. `save_ai_plan` inserts generated records atomically for the authenticated user. `profiles` contains name, age, and profession for AI personalization. The `supabase/config.toml` file contains local development configuration only.

## Initial relational conventions

- UUID primary keys generated by Postgres.
- `user_id uuid not null references auth.users(id)` on user-owned records.
- UTC `created_at` and `updated_at` timestamps; update timestamps maintained consistently.
- Foreign keys, check constraints, and indexes added with each migration.
- RLS enabled in the same migration as every user-owned table.
- Referential deletion rules documented; avoid cascading destructive changes across unrelated life areas.

## Candidate MVP entities

- `profiles` and `user_settings`, keyed by `auth.users.id`.
- `goals` and `goal_milestones`.
- `tasks` and, if recurrence/history requires it, `task_completions`.
- `habits` and `habit_entries`.
- `calendar_events`.

Use explicit relation tables when a task can associate with multiple goals or events. Decide recurrence representation before schema freeze. Keep private diary and finance schemas out of the first MVP migration.

## Ownership policy pattern

For each table, enable RLS and define policies for `SELECT`, `INSERT`, `UPDATE`, and `DELETE` where applicable, with `USING (auth.uid() = user_id)` and `WITH CHECK (auth.uid() = user_id)`. For child rows, verify the parent belongs to the same user. Client-side filtering is never an authorization control.

## Migration rules

Version all schema changes under `supabase/migrations/`. Migrations must be repeatable in a fresh local Supabase environment, avoid production data assumptions, and include policy changes alongside schema changes. Test both allowed-owner and denied-other-user access before release.
